# Organize collaboration around complete outcomes

First follow shared AGENTS rules to understand this task's purpose through the project, full message, current task, and originals. Fill understanding gaps with outside knowledge when needed; existing roles or familiar divisions must not define the task. Arrange responsibility according to the complete result and real dependencies, giving priority to the current user goal and authorization. Obtain applicable navigation and originals as needed; follow `evidence-research` for research operations.

A capable coordinator understands, delegates, coordinates, and communicates with the user. The responsible executor researches, implements, integrates, and delivers a complete outcome. Follow current AGENTS for tests and verification, without a fixed additional validation workflow. Select skills and tools by complete outcome, current stage, and execution responsibility; the person actually responsible reads them when needed, rather than the coordinator prereading every skill. One executor can implement first and read the writing skill later when producing substantive explanatory documents. A short final reply is not a document-writing stage. Assign responsibility by outcome and delegate only for independent outcomes, not mechanically by skills or steps such as “search, code, test,” or by opening a new window for each keyword. The responsible executor handles the core difficulty personally. Prefer scripts for repetition; independent judgment-heavy parts default to peer 6.1 Sol agents, with Astra used as needed for key design or effective challenge. Role presets are options, not mandatory stages. Claude hosts have no Sol/Astra: give independent judgment-heavy parts to `module-builder` or `general-purpose` (Sonnet), realistic feasibility of complex proposals to `feasibility-judge`, key design to `architect`, and effective challenge to `proposal-reviewer` (Opus; costly quota, use only for substantial plans or user requests). Claude's Agent tool already creates clean context; `fork_turns` and `create_thread` below apply only to Codex. These role/model defaults describe the source workflow; their availability must be established in the actual host.

## Decide how to divide the work

Consider actual value, dependencies, and ownership of independent work before assigning executors:

- **Outcome and input:** Can this part independently deliver a usable artifact, add independent evidence, or reduce the main window's material burden? Parallelize when input is available. If key input is missing, do parts that do not depend on it first; do not assign one person solely to wait for another's entire output. For new interfaces requiring alignment, specify current inputs, outputs, and the consumer. An interface still requiring verification cannot be described as connected.
- **Writes and resources:** Specify file or module ownership. Separate chats do not isolate files, browser authentication, cloud accounts, or production state. A shared resource has one explicitly responsible writer; others read existing artifacts or wait for a specific handoff. Use isolated directories/worktrees for code writes when necessary, while still addressing shared accounts and final merging. Do not build step-by-step signoff procedures.
- **Integration and burden:** Who connects the parts into the complete result the user wants? Assign an explicit responsible executor for interface integration, reading necessary original evidence, and truthful reporting of actual runtime results and unknowns. The coordinator must not collect summaries and redo the work. Consider running windows/subagents, additional model/tool expense, and coordination costs together. Headcount examples, empty slots, or role counts are not quotas; different levels must not delegate the same part again.

For a small single item, strongly sequential steps, or frequent edits to the same file, the current responsible executor completes the authorized work. Delegation is useful for independent material domains, separately verifiable modules, and different hypotheses that would change the plan. Judge from actual work, without fixed headcounts, depth, or reading-acknowledgement gates. Consult [Mature practices and failure boundaries](references/delegation-evidence.md) as needed for difficult divisions.

## Establish realistic feasibility before recommending complex plans

When a plan involves obtaining material, external services, sustained operation, multiple stages of dependency, or substantial investment, default to an independent dedicated feasibility judgment before recommendation. Codex uses `feasibility_judge` (6.1 Sol high) in new context with `fork_turns="none"`. Supply the complete goal, criteria, authorization, real conditions, user words, and shared task/outcome entry points, plus the candidate plan and its unverified evidence. The judge first independently identifies key dependencies from originals, then evaluates the candidate, rather than looking for risks solely from the responsible executor's conclusions. The AI fills missing originals. Do not mechanically add a role for small deterministic actions. Reuse established premises absent changed evidence, focusing on gaps that affect this approach.

The judge personally reads local, official, and relevant Chinese/domestic originals and, if necessary, makes a nondestructive sample in a specified new directory. Trace decisive links through “source and adaptation → actual acquisition → processing into usable material → subsequent execution and maintenance.” Nominal material scale is not usable quantity; platform entitlement is not authenticated access, actual invocation, or sustained operation. Provide evidence, units, and assumptions for cost/time, without inventing unmeasured numbers. When direct use is restricted, establish the specific restriction and continue investigating principles, learning from source code, adaptation, or independent implementation serving the original goal. Explain conditions still needing completion; do not stop at “cannot do,” generic risks, or silently reduced goals.

Save task-relevant key premises, original evidence and verification level, effect on the result, ways to fill gaps, actual costs/unknowns, smallest next action, and authorization boundaries in the specified outcome file. The responsible executor reads key originals and integrates tradeoffs. Judgment is not step-by-step approval or a user command; the user decides experience and substantive tradeoffs. Retain the responsibility over time but create instances per task. At completion, retain all evidence and unmet items; give later judgment to a new executor. The judge personally completes this round's evidence gathering and judgment without further delegation or commissioning another same-role judge to review itself. Reuse the same candidate without new evidence; do not trigger the role mechanically at every layer. Refer difficult key judgments to the responsible executor for independent Astra involvement as needed, avoiding duplicate checks.

If the current host cannot yet select the new role, a clean `default` loads the responsibilities from [integrations/agents/codex/feasibility_judge.toml](../../integrations/agents/codex/feasibility_judge.toml) and performs them with the same task and originals. A role registration file does not establish refresh in the running host. Claude uses registered `feasibility-judge`; if unavailable, clean `general-purpose` (Sonnet) takes the same responsibility without changing its global default model.

## Handoff and changes

Subagents also understand user intent and how their task relates to the complete goal. Delegation mainly supplies the shared task/progress entry point and the result to change now, with clear necessary conditions and file ownership. Research, design, and implementation remain the responsible executor's judgment. The coordinator may provide direction and advice with the problem and evidence it addresses; the executor decides adoption or adjustment after understanding it. Advice does not automatically become a user requirement. Do not copy background already in originals into long instructions. Brevity serves understanding; impose no word-count rule or prohibition on advice.

Sustained capability resides in project originals, shared memory, complete applicable tasks, and outcomes. A new delegation round after completion, rework, cross-stage handoff, independent module, or judgment from a different angle defaults to a new executor; do not reuse the predecessor merely for familiarity with history. Where supported, explicitly set internal new agents' `fork_turns="none"`. Create new user chats according to `create_thread`'s actual authorization; `fork_thread` inherits history and cannot substitute for clean handoff. Preserve the main thread in which the user is conversing, the user's explicitly assigned uses of original chats, and work currently in progress. Send live corrections to affected executors.

Start delegation with the deliverable, then entry points for the complete current task and necessary input originals, conditions that change the approach, and file ownership. In existing shared branches and outcomes, the AI maintains the complete goal, criteria, applicable conditions, necessary evidence, actual artifacts, and unmet items. Expand complex relationships and unresolved discussion through originals as needed. Short messages cannot replace these materials. Do not mechanically copy all history or ask the user to fill handoff forms. If the recipient cannot read files, include necessary prose directly. Reuse artifacts, tools, knowledge, and experience rather than depending on a predecessor remaining online or identical internal thinking in the new executor. Executors read needed skills at their usage stage. See [Clean-context delegation](references/fresh-context.md).

On new messages, understand them through the core goal, current task, effects on other branches, and existing outcomes before replacing affected methods; examples do not directly become fixed commands. When the user explicitly changes scope, inform affected executors while continuing other authorized tasks. Maintain complete goals, criteria, and progress only in the task's own shared-state branch; the parent main thread is not a substitute for this task.

## Outcomes and important reports

Executors keep ordinary progress in their own task. Proactively send usable artifacts, important evidence that changes other branches' methods, or specific blockers requiring coordination to the responsible person/direct consumer, including originals, impact, and advice. Specify which dependency is now usable and what remains missing. Do not broadcast every tool output or wait for the coordinator to ask. The coordinator processes important reports at natural work boundaries rather than repeatedly using `wait/read` for live supervision. Integrators inspect key originals and actual artifacts without rereading every process log.

Ordinary collaboration observations are material awaiting judgment, not user commands. They do not automatically change the goal or become completion gates. The responsible executor establishes technical facts; the user views actual work to judge experience and tradeoffs. Existing entry points, delivery, versions, reading acknowledgements, or successful local calculations cannot replace the result. Cross-chat messages must follow real user authorization and tool scheduling capabilities. Without a `Queue` parameter, do not promise noninterrupting delivery. Leaving material in an existing channel does not establish automatic wakeup either.

Deliver actual paths, verification level, and unmet items. Complete the handoff originals owned by you and stop this assigned work. Assign rework or later stages to a new executor rather than defaulting to further tasks for a completed agent. Save actual state before transferring write responsibility, remove the old writer from that part, and protect others' ongoing edits. Precisely retire replaced active rules and copies, retaining necessary recovery material only as cold storage. Follow the user's current [rules original](../../integrations/AGENTS.md) and [project-state method](../../integrations/prompts/project-state.md) for authorization, state, and cleanup, instead of duplicating a control rule set.
