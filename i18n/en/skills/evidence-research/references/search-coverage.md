# Search coverage, title catalogs, and continuation

Broad discovery first collects many titles, sources, and links for the AI to distinguish and expand. The search program retains every candidate actually returned by providers; it does not filter or highlight a few projects by stars, rank, hit counts, or literal overlap. Titles appear in collection order. Detailed descriptions, discovery queries, dates, and star counts remain in persistent originals for reading as needed.

`explore_search`, the local CLI, the Baidu MCP compatibility entry point, and explicit background work share `plugins/search-tools/`. The AI can supply a `queries` array directly; `terms` preserves original names without automatically appending recommendation, alternative, or awesome. Both enter the same persistent state. Broad entry points obtain pages from relevant Chinese and English engines separately; success with one does not replace the other. Engine lists describe interfaces supported by this implementation. The AI can extend through Bilibili site search, built-in web, author sites, and other available routes according to the task. Set `engines` and `sources` for the current purpose as needed. Run all CLI examples from the repository root.

`max_queries` is an optional web-request budget for this round. Omitting it applies no fixed query cutoff and no former 200-query cap. `dispatch_ms` defaults to 45000 and controls only how long this round continues dispatching requests. Undispatched items and failures are saved and returned; they cannot count as searched. Preserve request timeouts, provider throttling, and unreadable pages separately; switch to an independent route when blocked. `search_next` supplies parameters to continue the same goal. Normal continuation does not need `reset`; background work no longer resets state automatically either.

Web parsing retains all valid titles in the current response. When a next-page link or DDG pagination form is found, `pagination.next_request` supports actual continuation. Absence of an observed control means only that this response provides no continuation; it does not establish exhaustive domain coverage. `search_public` / `baidu_search` use `count` only as a provider page-size hint, without truncating parsed results.

GitHub does not request sorting by stars; pages contain 100 items and a single query returns at most 1000. Return `incomplete_results` and caps to the AI, which can change terminology, split questions, or switch sources according to the task. npm uses its documented 250-item page size and continues with `from`, without popularity weighting. The MCP registry continues through returned `metadata.nextCursor`. Tavily has no paginated search API and returns at most 20 items per response; explicitly report that provider cap. These are interface batches or service boundaries, not a rule to consider only the top N. Original evidence: [GitHub search](https://docs.github.com/en/rest/search/search), [npm search API](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md#get-v1search), [MCP Registry API](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/openapi.yaml), [Tavily search](https://docs.tavily.com/documentation/api-reference/endpoint/search).

The first response defaults to a compact title catalog and a small amount of continuation state. Titles prompt varied approaches; after connecting them to the goal and making an initial judgment, the AI freely selects originals or searches further, without reading the complete catalog first. Detailed request diagnostics are saved in complete originals; request `diagnostics=true` or CLI `--diagnostics` when needed. Returned `candidate_titles` is this compact title window; `catalog.total` is the full collection size; `catalog.next` gives lossless access to undisplayed items. `max_chars` defaults to 24000 and controls context display only, not candidate acquisition or persistence. If a complete record cannot fit, the result returns `required_chars`: increase the display budget rather than cutting the title. Background work defaults to a 4000-character title window for hook delivery and includes the complete catalog entry point. Short display cannot define the candidate boundary.

CLI usage (free-text arguments below are illustrative):

```powershell
node "plugins/search-tools/cli.mjs" explore --goal "Desired outcome and current research question" --terms "Industry term,Chinese term,newly discovered name" --mode topic
node "plugins/search-tools/cli.mjs" candidates --goal "The same goal" --max-chars 24000
node "plugins/search-tools/cli.mjs" candidates --goal "The same goal" --offset OFFSET_FROM_CATALOG --max-chars 24000
node "plugins/search-tools/cli.mjs" candidates --goal "The same goal" --details --ids "Candidate IDs selected by the AI"
node "plugins/search-tools/cli.mjs" expand --url "Source URL confirmed useful" --goal "The same goal"
```

Replace `OFFSET_FROM_CATALOG` with the returned number. Every link extracted during original-source expansion is saved; the implementation no longer sorts and saves only 40. Title windows and complete leads reside under `CODEX_HOME/context/recall-cache/search-explore/`; without `CODEX_HOME`, use the same relative location under the user's `.codex/`. Old system temporary caches can be imported. Related paragraphs are detail only; the AI decides whether they warrant further reading.

Already running MCP processes may retain old modules and tool metadata. Newly started compatibility entry points load official source files and new configuration. For current work, use the CLI to read current code rather than restarting the desktop or interrupting other tasks just to modify search. Saving or reading back a catalog proves only that leads are obtainable. Network pagination and sustained reduction in missed sources must still be demonstrated through subsequent real work.

The AI can save a query array as UTF-8 JSON, for example `["agent research query planning implementation", "研究智能体 搜索 阅读 分工"]`. This is an adaptable example, not a mandatory set of terms. CLI `explore` supports `--queries-file`; MCP `explore_search` supports a `queries` array; background `start` also accepts `--queries-file` and saves its contents at task start. Once called, the program executes valid supplied queries. Tool existence does not ensure that the host model proactively calls it.
