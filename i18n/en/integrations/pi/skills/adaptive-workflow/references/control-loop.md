General delegation, challenge timing, and exception handling follow [SKILL.md](../SKILL.md); evidence methods follow [adaptive-research](../../adaptive-research/SKILL.md). ## Peer challenge and actual response

Before discussion, supply challengers with the continuing goal, current proposal, key originals, and unverified premises. Select relevant categories from the error index. Let challengers independently investigate the proposal, alternatives, and counterexamples without loading the whole library or substituting an upper-layer summary for necessary originals. Peer challenge improves judgment; lower-layer implementers should not arbitrate proposals beyond their capability while interfaces remain unsettled.

The coordinator reads completed reports and records acceptance, partial acceptance, or rejection of key opinions with evidence-based reasons. Implement accepted items in the plan, code, or target asset. Preserve specific gaps and effects for unresolved items. Supplement evidence when insufficient; take over difficulties or reduce the package when capability is mismatched. Report existence, task termination, and verbal agreement do not prove implementation. Independent small implementations within an established route continue; only affected parts return to judgment. This does not add fixed headcount, serial stages, or approvals. If the formal binding protocol is used, retain the original requirements below.

## Bound proposals

When using the current installed `workflow_record` protocol, bind challenges to the same proposal version and follow the installed tool's schema and gates. The historical mechanism requires at least two completed challenge reports from different `root-peer` sessions. Receive every completed report through formal `read`; record acceptance, partial acceptance, or rejection with reasons for each, then decide `proceed`/`revise`/`stop`. Bound implementation for that version requires a valid controller `proceed` decision.

A terminal state such as `task_output` is not a formal receipt and does not establish understanding or approval. Report missing reports, unavailable formal records, or unmet gates honestly; do not fabricate receipts or decisions. Tool gates do not expand user authorization. Implementation remains subject to current user requirements, permissions, and runtime.
