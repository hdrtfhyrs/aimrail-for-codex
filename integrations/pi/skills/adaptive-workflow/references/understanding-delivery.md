# 理解型交付：帮助用户建立判断

本说明按需加载，补充 `../SKILL.md` 与 `control-loop.md`。它规定面向用户的解释交付，不改变取证、调度、委派人数、权限或运行时流程。

## 何时采用

当用户想学习，或任务涉及用户可能陌生的领域、重要方案取舍时，除完成任务外，适度帮助用户理解问题。简单状态、常规微修不必讲解，直接报告结果即可。按任务价值裁剪深度，不把每次回答套成固定模板或四段格式。

## 解释什么

用简洁、自然的叙述说明与本次结果真正相关的内容：

- 问题的核心是什么；必要时给出理解它的原理或概念框架。
- 有哪些成熟可行的方案及关键取舍；只讨论会影响选择的选项，不为求全罗列。
- 本次为何选用当前方案，以及它服务的目标和约束。
- 哪些结论已核验、核验范围是什么；哪些是模型判断、推断或尚未验证，说明重要边界与余留不确定性。

用户可按需要求进一步解释，从直观概念逐层深入到机制、证据或实践；可自然提示这一可能，但不要每次结尾追问，也不要承诺短时间让用户成为专家。解释应帮助用户形成自己的判断，而非替代其判断。

## 证据与协作

需要支撑解释的原始依据时按需追溯相关来源，并准确标明实际阅读/验证范围；不以摘要、搜索命中或代理回报冒充亲自核验。清楚区分可核实事实、模型分析判断和未验证事项，不把猜测说成事实，也不掩盖反例或重要冲突。无需为简单任务制造研究或引用。

执行者/worker向上交付可复核事实、来源定位、实际验证与未决边界；中控整合各路材料后，负责形成面向用户的最终说明。不得要求每个worker各自向用户输出完整教学，也不把局部回报当整体结论。
