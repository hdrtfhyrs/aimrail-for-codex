# 绑定挑战与决策闭环

按需读取，用于重要方案的独立挑战、实际回应及绑定协作记录。一般分工、何时挑战及异常处理见 [`../SKILL.md`](../SKILL.md)；证据取法见 [`../../adaptive-research/SKILL.md`](../../adaptive-research/SKILL.md)。

## 同级挑战与实际处置

讨论前让挑战者看到持续目标、当前方案、关键原始依据与未证假设；从错误库索引按相关性提供分类入口，由挑战者独立检验已有方案、替代方向和反例，不展开整库或用上层摘要代替必要原件。同级挑战用于改进判断，不让下级施工者在接口未定时承担超出能力的方案仲裁。

主控实际读取完成报告，对关键意见给出采纳、部分采纳或拒绝及证据理由；采纳项落实到方案、代码或目标资产，未决事项保留具体缺口和影响。出现依据不足时补证据，能力不匹配时接手难点或缩小施工包；不把报告存在、任务结束或口头赞同当作落实。已确定路线内独立小实现可继续，只有受新证据影响的部分返回判断；本段不增加固定人数、串行阶段或批准门槛。若采用正式绑定协议，则继续满足下述原有门槛。

## 绑定提案

使用当前 `workflow_record` 协议时，绑定同一提案版本执行挑战，并服从现装工具的 schema 与门槛。当前机制要求至少两份不同 root-peer 的已完成挑战报告；通过正式 `read` 收取每份完成报告后，逐份记录采纳、部分采纳或拒绝及理由，再作 `proceed`/`revise`/`stop` 决定。只有有效的控制器 `proceed` 决定后，才可进入该版本的绑定实施。

`task_output` 等运行终态不等于正式收据，也不表示已理解或批准。报告不全、正式记录不可用或门槛未满足时如实说明，不伪造收取或决定。绑定工具门槛不扩大用户授权；实施仍受当前用户要求、权限和运行时约束。

## 实际启动同级讨论（2026-09-25 接通）

在主控根会话先用 workflow_record 记录 proposal，再用 agent_batch 绑定同一 proposal_id、version 和 stage=challenge；每名同级讨论者显式选择与主控当前完全相同的 provider:model。该入口创建独立讨论会话，沿原有报告、read 和 decision 流程收取与处置；不会套用普通施工的 Sol→Luna 派发完成要求。brief 带当前方案、相关原证和少量匹配错误案例，要求实际阅读并提出可核对的反例。其他型号不会仅因标记 challenge 就被称为同级；普通施工与嵌套路线保持原规则。当前已做隔离运行链验证，不能将其说成真实模型审查质量保证。
